# VesPN — самораскатывающаяся панель управления VPN

Небольшая self-hosted веб-панель, которая **сама разворачивает и обслуживает ваш
парк VPN-серверов**. Вы даёте ей SSH-доступ к чистому серверу на Debian — она ставит
всё необходимое, настраивает, поднимает фейловер и следит за состоянием. Руками ни
одну ноду трогать не нужно. Ваши пользователи заходят и сами генерируют себе конфиги
**VLESS (Reality)** и **AmneziaWG**.

Панель построена под конкретную сложную задачу: держать надёжный VPN **из региона с
активной DPI-цензурой** (исходное развёртывание живёт под российским ТСПУ). Архитектура
исходит из того, что выходные серверы будут блокировать, что релей перед ними стоит на
враждебной территории, а сам Telegram может быть недоступен — и всё равно продолжает
работать.

> **Одним предложением:** вы описываете в панели нужный парк серверов, а она превращает
> набор голых машин в устойчивый к цензуре самовосстанавливающийся VPN — и потом сама
> себя бэкапит и сообщает (через Telegram), когда что-то сломалось.

## Зачем это нужно / архитектура за минуту

Обычная схема «один VPN-сервер» умирает в тот момент, когда его IP блокируют, и каждому
клиенту приходится всё перенастраивать. VesPN разделяет две работы, которые делает
VPN-сервер:

- **Гейты (gates)** — дешёвые релеи *внутри* региона с цензурой. Гейт — это прозрачный
  **L4-форвардер**: он DNAT-ит шифротрафик напрямую на выходную ноду и **ничего не
  расшифровывает**. Гейты собраны в **пулы гейтов**: все гейты пула держат одинаковый
  релей, клиент может войти через любой, а гейт — расходник (добавить или заменить его =
  поправить DNS, конфиг клиента не меняется). Так как гейт не держит ключей и видит только
  шифротекст, его изъятие или прослушка ничего не раскрывают.
- **Пулы выходов (exit pools)** — набор серверов за рубежом, которые реально выходят в
  интернет. Каждый выход в пуле — **криптографический клон** соседей (одинаковые ключи
  Reality / серверный ключ AmneziaWG / порты / таблицы клиентов), поэтому **один конфиг
  клиента проходит аутентификацию на любом из них**. Гейт проверяет здоровье пула и сам
  переключает трафик на живой выход — без какой-либо перенастройки у клиента.

```
                    ┌─────────────────── пул выходов «eu» ──────────────────┐
                    │  (криптоклоны — один конфиг подходит ко всем)          │
  клиент ─VLESS/AWG─►  гейт (RU)  ──►  выход #1  (приоритет 10, АКТИВЕН) ──► интернет
  (звонит гейту)     L4-релей,     │   выход #2  (приоритет 20, резерв)
                     не расшифр.   │   выход #3  (приоритет 30, резерв)
                                    └─────────────────────────────────────────┘
          ▲                                   ▲
          │ self-service конфиги              │ SSH (paramiko) — установка, клон,
          │                                   │ синхронизация, чтение здоровья
     ┌──────────┐                        ┌──────────┐
     │  юзеры   │                        │  панель  │  ← это приложение («Hub»)
     └──────────┘                        └──────────┘     хранит всё состояние+секреты;
                                                           сама трафик НЕ пропускает
```

**Сама панель не пропускает VPN-трафик** — это малозаметный control plane, который
управляет каждой нодой по SSH и достукивается до локальных админ-API нод через SSH-туннели
по требованию. БД панели — единственный источник правды; ноды сводятся (converge) к ней.

**Доступ к нодам — по ключу парка.** Панель владеет одним SSH-ключом (Ed25519), который
**генерируется на Хабе при первом старте** и хранится в БД **в зашифрованном виде** (тем же
`PANEL_SECRET_KEY`); приватная часть Хаб не покидает. Root-пароль ноды нужен только для
**первого** подключения: при раскатке панель кладёт публичный ключ парка в `authorized_keys`
ноды (`provisioning.install_fleet_key`) и дальше ходит по ключу (paramiko пробует ключ,
при неудаче — пароль, что и даёт бесшовный бутстрап). Публичный ключ можно вставить и при
создании VM — тогда пароль root не нужен вовсе. Статус ноды в «Парке» показывает `🔑 ключ`
или `🔒 пароль`; сам публичный ключ и его отпечаток — там же, в блоке «Ключ парка».

Выход в пуле панель администрирует **только через гейт** (SSH-ProxyJump): DPI в
регионе с цензурой часто рвёт прямое SSH-рукопожатие Hub→выход на «грязных» диапазонах, а
гейт до выхода достукивается, поэтому управляющий SSH туннелируется через гейт (сам гейт
только пересылает байты и к выходу не аутентифицируется). Подходит **любой гейт** пулов
гейтов, через которые ходят маршруты этого пула: панель пробует их по приоритету и берёт
первый, что ответил, — потеря одного гейта не отрезает панель от выходов. Прямого
соединения Hub→выход панель **не открывает сама никогда**, автоотката нет — если ни один
гейт не провёл, операция падает с понятной ошибкой (а не виснет на DPI). Исключение —
пул, который используют только **прямые** маршруты (без гейтов): его клиенты и так ходят
на серверы напрямую, и панель тоже. Порядок раскатки: сначала гейт, затем выходы, которые
к нему привязываются; раскатка выхода требует, чтобы гейт пула был известен заранее. На случай, когда выход недоступен через гейт, в «Серверах» есть кнопка
**«Напрямую ⚠»** — разовая диагностика прямым подключением, с предупреждением, что трафик
пойдёт в обход гейта. Так «добавить выход через сайт» работает и для флагнутых диапазонов.

## Что она умеет (восемь задач, под которые сделана)

| # | Возможность | Как |
|---|-------------|-----|
| 1 | **Разворачивать гейты** (L4-релеи насквозь) | `nftables` DNAT + крошечный демон health-check на Python, доставляемые по SSH; пропускает шифротекст, не расшифровывает |
| 2 | **Разворачивать выходы** (VLESS + AmneziaWG) | Ставит то, что нужно маршрутам пула: mainline 3x-ui с inbound VLESS+XHTTP+Reality (у старых пулов — TCP+Reality+Vision) и/или контейнер AmneziaWG — всё с общей идентичностью пула |
| 3 | **Администрировать конфиги клиентов** | Self-service: юзер добавляет устройства, получает QR / ссылку / файл (AmneziaWG — `.vpn` для AmneziaVPN на Android/ПК, и отдельный WireGuard-style `.conf` для iOS/iPhone); один конфиг на устройство, валиден на весь пул |
| 4 | **Проверять доступность — два независимых среза** | Hub → каждый сервер (плоскость управления) **и** каждый гейт → выходы своего пула (реальный путь клиента, читается из демона гейта) |
| 5 | **Фейловер при потере выхода** | **Делает сам гейт** (active/standby с гистерезисом); панель задаёт приоритеты и шлёт список членов пула |
| 6 | **Бэкапить себя** | Консистентная онлайн-копия БД панели + секреты для восстановления, ежедневно в Telegram и по запросу |
| 7 | **Мониторить состояние** | Сохранённый снапшот, отрисованный на админ-странице и в Telegram; почасово + по запросу |
| 8 | **Уведомлять через Telegram — даже когда Telegram заблокирован** | Настраиваемый API-base + реверс-прокси, который панель может поднять на выходе одной командой (DuckDNS + Let's Encrypt → `api.telegram.org`) |

## Ключевые понятия

- **Пул (pool)** — криптоидентичность (пара ключей Reality + shortIds + spiderX + порт,
  и серверный ключ AmneziaWG + PSK + параметры обфускации + порт), сгенерированная один
  раз в панели. Каждый выход, добавленный в пул, разворачивается как её **клон**. Какие
  протоколы работают на серверах пула, следует из его маршрутов: один сервер может нести
  несколько протоколов — у пула тогда по маршруту на каждый.
- **Выход (exit)** — сервер, который запускает VPN и выходит в интернет. Принадлежит
  одному пулу. Имеет `priority` (меньше = предпочтительнее) и `sync_state` (трафик идёт
  только на `synced`-выходы).
- **Гейт (gate)** — релей в регионе с цензурой перед пулом. К нему обращаются клиенты.
- **Пул гейтов (gate pool)** — набор взаимозаменяемых гейтов с одинаковым релеем. Один пул
  гейтов может обслуживать **несколько маршрутов** (например, разных протоколов); `priority`
  гейта задаёт, через какой панель управляет выходами в первую очередь.
- **Маршрут (route)** — **протокол** (`vless` / `naive` / `awg`) **+** вход (**пул гейтов**
  или **напрямую**) **+** пул серверов. Устройство получает конфиг только на маршруте своего
  протокола; маршрут без протокола — «старый» (до разделения по протоколам) и обслуживает
  и VLESS, и AmneziaWG. Клиент выбирает маршрут сам — из тех, к которым ему открыт доступ
  по группе. Сменить регион
  выхода = выбрать другой маршрут; конфиг при этом не меняется. Перевести маршрут на другой
  пул гейтов («Сменить вход» на «Парке») тоже можно без новых конфигов: клиенты ходят на
  адрес маршрута, а не на конкретный гейт.
- **Роли.** `admin` — полный доступ, включая управление ролями людей; `operator` — то же над
  парком, клиентами, группами и маршрутами, **кроме** управления ролями; `client` — конечный
  пользователь. У каждой учётки на странице «Пользователи» видно, **кем она заведена**.
- **Группы доступа.** Пользователь может состоять в нескольких группах; маршруту назначаются
  группы, которым он разрешён. Клиент видит маршрут, если делит с ним хотя бы одну группу;
  маршрут без групп недоступен никому. Персонал (admin/operator) видит и может делать конфиги
  по **всем** включённым маршрутам, минуя группы.

## Быстрый старт (Docker)

```bash
cp .env.example .env
# отредактируйте .env: задайте PANEL_SECRET_KEY (openssl rand -base64 48) и ADMIN_PASSWORD
docker compose up -d --build
# по умолчанию панель публикуется на 127.0.0.1:8080 (см. PANEL_BIND)
```

Заходите через SSH-туннель (панель держит доступы ко всему парку — не выставляйте её
голой наружу):

```bash
ssh -L 8080:127.0.0.1:8080 root@<хост-панели>
# затем откройте http://127.0.0.1:8080 и войдите админом из .env
```

### Публичный HTTPS

Есть два оверлея:

```bash
# A) у вас свободны порты 80/443 и домен указывает на хост панели:
docker compose -f docker-compose.yml -f deploy/docker-compose.tls.yml up -d --build

# B) порты 80/443 заняты / нужен бесплатный TLS без них — DuckDNS DNS-01,
#    отдаётся на :8443 (сначала задайте PANEL_DOMAIN + DUCKDNS_TOKEN в .env):
docker compose -f docker-compose.yml -f deploy/docker-compose.duckdns.yml up -d --build
```

## Поднять парк (всё из интерфейса)

Всё ниже делается в браузере — **как только SSH-доступ сервера попал в панель, вы на него
больше не заходите.** В этом суть: добавил сервер через сайт — он сам себя настроил.

1. **Пулы → создать пул** (`eu`). Панель генерирует общую криптоидентичность.
2. **Серверы → добавить ноду** для гейта: роль = *gate*, его публичный IP + SSH.
   Добавьте гейт **до** раскатки выходов: выходы на флагнутых диапазонах панель ставит
   *через* него (SSH-ProxyJump), иначе прямое SSH Hub→выход может не пройти.
3. **Серверы → добавить ноду** для каждого выхода: имя, публичный IP, SSH root-доступ,
   роль = *exit*, пул = `eu`. Затем **Развернуть** — панель (при необходимости через гейт)
   ставит 3x-ui, пинит Xray, создаёт VLESS-inbound с ключами пула, разворачивает контейнер
   AmneziaWG, закаляет машину и синхронизирует её в пул. Повторите для каждого выхода;
   задайте `priority`, чтобы один был основным, а остальные — резервом.
4. **Парк → «Создать маршрут»**: имя, протокол, серверы (новый пул или существующий — тогда
   протокол добавится к его серверам) и вход — существующий пул гейтов, свободный гейт (из
   него получится новый пул гейтов) или «напрямую». «Парк» разбит на три блока —
   **Маршруты**, **Пулы гейтов**, **Пулы серверов**: гейты добавляются в пул гейтов
   («+ Гейт»), выходы — в пул серверов («+ Выход»). **Поднять релей** — у пула гейтов
   (релей — его свойство и собирается из всех его маршрутов): панель ставит на **каждый**
   гейт пула демон health-check, нацеленный на выходы (в порядке приоритета). Один пул
   гейтов может обслуживать маршруты разных протоколов и разных пулов серверов: TCP-порт,
   общий для нескольких TLS-маршрутов, гейт разводит по SNI (см. «Фейловер подробно»);
   конфликты панель показывает у пула гейтов заранее. Пул (гейтов или серверов), который используют
   маршруты, удалить нельзя — сначала смените им вход или удалите их; удаление маршрута
   пулы и серверы не трогает.
5. **Пользователи → «Группы доступа» → создать группу.** На вкладке **Парк** у маршрута
   отметьте, какой группе он доступен; людей в группу добавляйте прямо в таблице пользователей
   (кнопка «＋ в группу» в строке) — пользователи и группы живут на одной вкладке.
6. **Пользователи → создать пользователя** (по умолчанию — клиент; операторов/админов заводит
   только админ). Он заходит, **выбирает доступный маршрут**, добавляет устройства и получает
   конфиги. Готово.

> **Долгие операции идут в фоне.** «Развернуть»/«Переразвернуть» и «Поднять релей» — это
> минуты SSH-работы. Панель запускает их фоновым потоком и отвечает сразу, поэтому обратный
> прокси (Cloudflare на free-тарифе рвёт ответ на 100-й секунде — ошибка 524) их не обрывает.
> На «Парке» у ноды виден статус (идёт / готово / ошибка с текстом), кнопка на время работы
> заблокирована (повторный клик не запустит вторую раскатку), а страница сама обновляется по
> завершении. Реализация — `app/jobs.py`; состояние job хранится на самой ноде, а «зависший»
> после перезапуска панели статус сбрасывается в ошибку на старте.

> **VLESS: транспорт и маскировка — настройки пула серверов** («Парк» → пул → «VLESS: …»).
> Новые пулы — **VLESS + XHTTP + Reality** (по отчётам 2026 года держится лучше голого
> TCP+Reality; путь XHTTP генерируется случайный), пулы, созданные раньше, остаются на
> TCP + Reality + Vision — так написано в их выданных конфигах. Сайт-маска Reality (`target`)
> и SNI, на которые отвечает inbound, по умолчанию берутся из
> `app/data/vless_inbound_template.json` (`www.sony.com` + региональные домены Sony), но у
> пула могут быть свои: это нужно, чтобы гейт развёл два Reality-пула на одном порту, и
> удобно для маски «по соседству» с гейтом (сайт с того же хостинга). Всё это — часть
> клиентских конфигов: после смены переразверните серверы пула, поднимите релей и
> перевыпустите VLESS-конфиги пула.
>
> **Ссылку VLESS панель собирает сама** — из идентичности пула (ключ Reality, shortId,
> spiderX, SNI, транспорт) и адреса маршрута (имя хоста или первый вход, порт для клиентов;
> у новых маршрутов по умолчанию 443), без запроса к 3x-ui. На выходы 3x-ui лишь заводит
> клиента с тем же uuid. Сменили адрес маршрута — ссылка на странице устройства обновится
> сама.
>
> **Что ставится на выход**, следует из маршрутов его пула: VLESS — 3x-ui с inbound, AWG —
> контейнер AmneziaWG; ненужное не ставится. Поэтому у пула должен быть хотя бы один
> маршрут, прежде чем разворачивать его серверы.
>
> **AmneziaWG 3.1.** Новые пулы генерируют параметры **3.1**: защита заголовков
> (`HeaderProtectionKey` — заголовки пакетов выглядят случайными), случайное дополнение
> пакетов (`ContentPaddingAddition`), «плавающие» таймеры протокола (rekey/reject/keepalive
> — диапазонами), `RandomTrailers`, без cookie-ответов (`DisableCookies`), плюс сигнатурный
> пакет `I1` в форме QUIC Initial перед каждым рукопожатием. Значения по умолчанию — как у
> клиента Amnezia; имена параметров одни и те же в `awg0.conf`, в `.conf` для iOS и в JSON
> строки `vpn://` (тип контейнера в приложении прежний, `amnezia-awg2`, `protocol_version`
> = `3.1`). Нужен **AmneziaVPN 5.0.1.5+**; MTU 1280. Пулы, созданные раньше, остаются на 2.0
> (их выданные конфиги не меняются). Образ сервера закреплён (`AWG_IMAGE`,
> `amneziavpn/amneziawg-go:3.1.20260828`) вместо `latest`: движок 3.1 обслуживает и
> 2.0-конфиги. У прямого маршрута порт для клиентов — порт сервера пула (гейта, который
> переназначил бы порт, нет): для AWG на UDP 443 задайте «AWG порт» = 443 при создании пула.

Нарастить ёмкость позже = добавить выход в пул, **Развернуть**, затем заново **Поднять
релей**, чтобы гейты узнали о новом члене. Потеря выхода действий не требует — гейт
переключится сам.

> **Обновление со старой схемы.** Раньше у маршрута был ровно один гейт. При первом старте
> новой версии каждый такой гейт автоматически становится пулом гейтов из одного гейта (с его
> именем), а маршрут — ссылается на этот пул; ничего перенастраивать не нужно.

## Подписки

У VLESS-устройства, кроме одиночной ссылки, есть **подписка** — один URL на устройство
(страница устройства: ссылка, QR, «Перевыпустить ссылку»). Приложение (v2rayNG, OneXray,
v2rayN, Happ…) раз в `SUB_UPDATE_HOURS` (по умолчанию 12) перекачивает список входов, поэтому
гейты, которые появляются или выпадают, доходят до устройства сами — новый конфиг раздавать
не нужно.

Что в подписке: все включённые VLESS-маршруты, доступные владельцу (маршрут устройства
первым), и для каждого:

- **«… · авто»** — по имени хоста маршрута (его A-записи панель держит на живых входах, см.
  «DNS входов»): ядро клиента перебирает адреса само, мёртвый гейт пропускается без действий
  пользователя;
- **по записи на каждый гейт по IP** (у прямого маршрута — на каждый сервер) — ручной резерв
  на случай, если само имя заблокировано на DNS провайдера.

Клиент VLESS (один uuid на устройство) поэтому заводится на серверах **всех** пулов, чьи
VLESS-маршруты доступны владельцу; синхронизация пула приводит набор клиентов к этому же
правилу (и снимает клиента, у владельца которого отобрали доступ ко всем маршрутам пула), а
трафик считается со всех таких пулов.

Формат выбирается по User-Agent приложения (или `?format=base64|singbox`): по умолчанию —
base64-список `vless://`; для Karing / sing-box / Hiddify — JSON sing-box с группой `urltest`
(приложение само переключается на рабочий вход). В sing-box нет XHTTP, поэтому в JSON идут
только записи, которые он умеет; если таких нет — отдаётся base64-список. В ответе —
`profile-title`, `profile-update-interval`, `subscription-userinfo` (трафик устройства).

Безопасность: токен — 192 случайных бита; неизвестный/отозванный токен, чужой хост и
превышение лимита запросов с IP дают одинаковый голый 404 (фронт-прокси может подменить его
404-страницей сайта). Перевыпуск ссылки сразу отзывает старую. `SUB_BASE_URL` — публичный
адрес подписок на **своём** хосте: если задан, `/s/<токен>` отвечает только на нём, а
фронт-прокси должен пускать на этот хост только `/s/*`. AmneziaWG в подписках нет — его
конфиг статический.

## Фейловер подробно

На гейте работает небольшой демон (`/usr/local/bin/vespn-relay-daemon.py`, systemd-юнит),
который:

- читает **план релея** из `/etc/vespn-relay/members.json`. План панель собирает из **всех
  маршрутов пула гейтов** (`app/relay.py`): для каждого пула серверов — его члены в порядке
  приоритета, для каждого клиентского порта — куда его пересылать;
- TCP-пробит каждый сервер раз в несколько секунд, с **гистерезисом** (член должен
  пройти/провалить пробу *дважды* подряд, чтобы сменить статус — не дёргается от одной
  неудачной пробы); у пула только с AmneziaWG пробится SSH-порт (жив ли хост);
- держит вход гейта направленным на **единственный живой сервер с наивысшим приоритетом**
  в каждом пуле (active/standby). Когда тот падает, трафик уходит на следующий живой; когда
  восстанавливается — возвращается обратно.

Как гейт пересылает:

- **порт с одним получателем** (один пул серверов + порт) — DNAT в ядре (`nftables`), TCP или
  UDP; порт на гейте может отличаться от порта на сервере;
- **TCP-порт, который делят несколько TLS-маршрутов** (VLESS-Reality и NaiveProxy на 443,
  два Reality-пула с разными SNI) — разводится по **SNI** из ClientHello: HAProxy в режиме
  TCP читает имя и передаёт соединение нужному пулу, **TLS не завершает** (ставится на гейт
  автоматически, только если такой порт есть; юнит `vespn-sni`). Неизвестный SNI уходит
  первому бэкенду порта — у Reality это настоящий сайт-маска;
- **UDP по SNI не развести** — два AmneziaWG-маршрута в одном пуле гейтов должны иметь
  разные клиентские порты.

Конфликты (два маршрута с одним SNI на одном TCP-порту, маршрут без SNI на общем порту, два
UDP-маршрута на одном порту) панель находит заранее: пул гейтов на «Парке» показывает «релей
не собрать: …» с подсказкой, что поменять, и кнопку релея не даёт. Гейты со старым
форматом `members.json` после обновления демона продолжают работать как прежде.

Гейт пересылает только шифротекст. Клиенты ничего не замечают — тот же адрес, тот же
конфиг. Панель не в тракте данных, и для фейловера её работоспособность не нужна.

## Мониторинг и алерты

**Серверы → Мониторинг** (и Telegram-бот) показывают два намеренно разделённых среза, и
**ни один не делает прямого Hub→выход** (выходы проверяются только с их гейта):

- **Управляемость: Hub → ноды** — может ли панель управлять нодой своим реальным путём: до
  гейтов напрямую (SSH), до выходов — через их гейт (TCP-проба SSH-порта выхода **с гейта**).
  Это плоскость управления; связность клиента она **не** отражает.
- **Клиентский путь: гейт → выходы** — с **каждого** гейта пула гейтов: достижимость выходов
  по портам трафика (VLESS/AWG), плюс живое состояние релей-демона для этого пула серверов:
  какие выходы он видит живыми, какой активен прямо сейчас и сколько раз активный выход
  «дёргался» (флаппинг) за последний час.

Проверки идут почасово (настраивается), по кнопке на странице и по `/check` в Telegram.
Эскалируются как алерты только клиентозначимые состояния: любой гейт пула упал (это сигнал
бана, даже если остальные гейты маршрут держат), демон релея мёртв, **нет** живого выхода,
флаппинг, и отдельно — у маршрута не осталось **ни одного** рабочего гейта.

**Журнал гейтов.** Гейты — расходники, и их банят; после бана важно знать, *когда*, *с какой
стороны* и *под какой нагрузкой*. Каждые `JOURNAL_MINUTES` (по умолчанию 5) панель для
каждого гейта: открывает TCP к его SSH-порту **с Hub** (изнутри региона — примерно как гейт
видят клиенты) и **с сервера за рубежом** (любого, до которого дотянулась в этот раз), а по
SSH снимает счётчики трафика интерфейса и число клиентских IP в conntrack на портах релея.
«Доступен из-за рубежа, но не с Hub» — заблокирован для региона; «недоступен ни оттуда, ни
оттуда» — отрезан у хостера/вышестоящего оператора. Страница **Журнал гейтов**: текущее
состояние, когда впервые пропал с каждой стороны, трафик и клиенты за период, переходы.
Замеры хранятся 90 дней.

**DNS входов.** У маршрута можно задать имя хоста для клиентских конфигов и DNS-провайдера
его зоны (Cloudflare, deSEC или dynv6; «Парк» → DNS-провайдеры, токен хранится
зашифрованным). После каждого замера журнала панель держит в A-записях имени IP **живых**
входов маршрута: гейтов пула, которые Hub ещё достаёт (гейт выпадает после двух неудачных
замеров подряд), а у прямого маршрута — синхронизированных серверов. Пустым имя не
становится никогда: если живыми не числится никто, остаются все. API провайдера дёргается
только при изменении набора (и раз в 6 часов — сверка).

**Переключение выхода сбрасывает старые соединения.** Когда демон гейта переводит пул на
другой сервер, он удаляет из conntrack записи к старому (`conntrack -D --reply-src`): иначе
UDP-клиент, который постоянно шлёт keepalive (AmneziaWG), оставался бы привязан к мёртвому
серверу, пока не замолчит.

**Трафик по конфигам.** Отдельная страница **Трафик** (админ/оператор): сколько у каждого
пользователя конфигов и сколько трафика по каждому — за день и всего. Счётчики снимаются
периодически **через гейт** (VLESS — API 3x-ui, AmneziaWG — `awg show transfer`), суммируются
по пулу и накапливаются с учётом сбросов счётчиков. Прямого Hub→выход при сборе нет.

## Telegram-бот (работает из заблокированного региона)

Опционально. Работает фоновыми потоками внутри процесса панели; спит, пока не заданы токен
+ chat id (в **Мониторинг → настройки бота**, хранится в БД в зашифрованном виде).

- **Ежедневно:** бэкап (см. ниже) + сводка статистики.
- **Почасово:** мониторинг; шлёт админу алерт, когда набор проблем меняется.
- **Команды:** `/check` (проверить сейчас), `/status` (последний снапшот), `/backup`
  (прислать сейчас).

**Проблема заблокированного Telegram, решённая через гейт.** `api.telegram.org` недоступен
из региона, где живут гейт/панель. На **каждом выходе** автораскатка поднимает реверс-прокси
Caddy, слушающий только `127.0.0.1` (наружу ничего не торчит). Бот не ходит ни в Telegram
напрямую, ни к выходу напрямую: он открывает SSH-туннель **Хаб→гейт→выход** и обращается к
прокси через него (SSH шифрует хоп, Caddy добавляет TLS до Telegram). Выход для ТГ выбирается
**по приоритету** (`Node.priority`): бот берёт первый достижимый и переключается на следующий,
если тот отвалился. Так закрыт последний прямой Hub→выход.

Поле **API-base** остаётся как ручной обход: если задать явный внешний URL (не
`api.telegram.org`), бот пойдёт по нему напрямую, минуя гейт (для отладки).

## Бэкап

`make_backup()` формирует `.tar.gz` с **консистентной** онлайн-копией SQLite-БД панели
(через backup-API SQLite — никогда не рваный файл) плюс `env.txt` с секретами для
восстановления (`PANEL_SECRET_KEY`, доступы админа, домен/токен DuckDNS, …). Отправляется
ежедневно в Telegram и по `/backup`.

> ⚠️ **Бэкап чувствителен.** Вместе с `PANEL_SECRET_KEY` он расшифровывает любой
> сохранённый доступ к ноде. Держите Telegram-чат приватным; относитесь к архиву как к
> мастер-ключу.

## Модель безопасности и заметки

- **Гейт по замыслу не доверенный.** Он всегда видит только шифротекст и не держит ключей,
  поэтому его безопасно крутить на враждебной территории. Zero-trust — это и есть вся суть.
- **Секреты в покое.** SSH-пароли, API-токены 3x-ui и ключи пула шифруются в БД через
  Fernet ключом, производным от `PANEL_SECRET_KEY`. Его ротация намеренно делает их
  нечитаемыми (введёте заново из UI).
- **Ноды закаляются автоматически** при провижининге: панель 3x-ui слушает только
  `127.0.0.1` (доступна исключительно через SSH-туннель панели), публичный
  subscription-сервер выключается, `fail2ban` отключается (иначе он забанит гейт или
  панель при всплеске подключений), а Xray-core пинится на заведомо рабочую версию.
- **Защищайте панель.** Она держит доступы ко всему парку — прячьте её за SSH/HTTPS,
  никогда не выставляйте напрямую, и поставьте `SESSION_HTTPS_ONLY=true`, как только она на
  HTTPS.
- **Перебор паролей.** Неудачные входы считаются в скользящем окне 15 минут: 5 ошибок с
  одного IP на один логин или 20 с одного IP на любые логины — дальше вход с этого IP
  отклоняется, пароль даже не проверяется, пока окно не освободится. По одному логину
  без IP не блокируется: иначе чужой мог бы запереть настоящего пользователя. Счётчики в
  памяти и сбрасываются при рестарте. Каждая ошибка пишется в лог
  (`login failed from <ip>`), блокировка — `login throttled from <ip>`.
- **Настоящий IP за прокси.** Если перед панелью reverse proxy в другом контейнере
  (оверлеи из «Публичный HTTPS»), задайте `FORWARDED_ALLOW_IPS=*` — тогда uvicorn берёт
  адрес посетителя из `X-Forwarded-For`, а не адрес прокси (иначе все посетители — «один
  IP», и лимит по IP запирает всех сразу). Делайте это, только если порт панели не
  доступен снаружи напрямую: иначе заголовок можно подделать. Оверлеи из `deploy/` это
  уже задают.
- **Требования к паролю:** не короче 8 символов, буквы и цифры (спецсимволы не нужны), без
  логина внутри и не из списка самых частых. Проверяются при смене пароля. Пароль, заданный
  до появления правил (или слабый `ADMIN_PASSWORD`), пускает один раз и сразу отправляет
  на смену.
- Приватные ключи клиентов AmneziaWG генерируются на стороне панели и живут **только** в
  выданном конфиге (внутри строки `vpn://`); на ноду они никогда не попадают.

## Темы оформления

Внешний вид панели можно сменить, не трогая её код: укажите в `.env` каталог темы и
смонтируйте его в контейнер.

```env
THEME_DIR=/theme          # каталог темы внутри контейнера
BRAND_NAME=Моя сеть       # название в шапке, на странице входа и в заголовках вкладок
```

```yaml
# docker-compose.override.yml
services:
  panel:
    volumes:
      - ./my-theme:/theme:ro
```

Структура темы (всё необязательно, чего нет — берётся штатное):

```
my-theme/
├── static/                 отдаётся как /theme/...
│   └── theme.css           подключается после штатного style.css
└── templates/              переопределяет одноимённые штатные шаблоны
    ├── _head.html          шрифты, favicon (штатно — Google Fonts)
    ├── _brand.html         знак и название в шапке и на входе
    └── _auth_aside.html    украшение над формой входа (штатно пусто)
```

Почти весь вид задаётся CSS-переменными из `app/static/style.css` (`--bg`, `--panel`,
`--accent`, `--font-display`, `--radius`…) — обычно теме достаточно переопределить их в
`theme.css`. Переопределять целиком страничные шаблоны (`dashboard.html` и т. п.) тоже
можно, но тогда тему придётся сверять с каждым обновлением панели.

## Стек

FastAPI · SQLAlchemy (SQLite) · Jinja2 · paramiko (SSH + туннели) · bcrypt ·
`cryptography` (генерация ключей WG/Reality + Fernet). Без брокера сообщений, без внешней
БД — один процесс, один файл SQLite в volume. Ноды крутят mainline 3x-ui + официальный
контейнер `amneziavpn/amneziawg-go`; гейты — `nftables` + демон на ~90 строк из stdlib.
