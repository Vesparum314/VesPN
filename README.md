# VesPN — самораскатывающаяся панель управления VPN

Небольшая self-hosted веб-панель, которая **сама разворачивает и обслуживает ваш
парк VPN-серверов**. Вы даёте ей SSH-доступ к чистому серверу на Debian — она ставит
всё необходимое, настраивает, поднимает фейловер и следит за состоянием. Руками ни
одну ноду трогать не нужно. Ваши пользователи заходят и сами генерируют себе конфиги
**VLESS (Reality)** и **AmneziaWG**.

Панель построена под конкретную сложную задачу: держать надёжный VPN **из региона с
активной DPI-цензурой** (исходное развёртывание живёт под российским ТСПУ). Архитектура
исходит из того, что выходные серверы будут блокировать, что релей перед ними стоит на
враждебной территории, а сам Telegram может быть недоступен — и всё равно продолжает
работать.

> **Одним предложением:** вы описываете в панели нужный парк серверов, а она превращает
> набор голых машин в устойчивый к цензуре самовосстанавливающийся VPN — и потом сама
> себя бэкапит и сообщает (через Telegram), когда что-то сломалось.

## Зачем это нужно / архитектура за минуту

Обычная схема «один VPN-сервер» умирает в тот момент, когда его IP блокируют, и каждому
клиенту приходится всё перенастраивать. VesPN разделяет две работы, которые делает
VPN-сервер:

- **Гейты (gates)** — дешёвые релеи *внутри* региона с цензурой. Гейт — это прозрачный
  **L4-форвардер**: он DNAT-ит шифротрафик напрямую на выходную ноду и **ничего не
  расшифровывает**. Клиент всегда обращается только к гейту, поэтому конфиг клиента
  никогда не меняется. Так как гейт не держит ключей и видит только шифротекст, его
  изъятие или прослушка ничего не раскрывают.
- **Пулы выходов (exit pools)** — набор серверов за рубежом, которые реально выходят в
  интернет. Каждый выход в пуле — **криптографический клон** соседей (одинаковые ключи
  Reality / серверный ключ AmneziaWG / порты / таблицы клиентов), поэтому **один конфиг
  клиента проходит аутентификацию на любом из них**. Гейт проверяет здоровье пула и сам
  переключает трафик на живой выход — без какой-либо перенастройки у клиента.

```
                    ┌─────────────────── пул выходов «eu» ──────────────────┐
                    │  (криптоклоны — один конфиг подходит ко всем)          │
  клиент ─VLESS/AWG─►  гейт (RU)  ──►  выход #1  (приоритет 10, АКТИВЕН) ──► интернет
  (звонит гейту)     L4-релей,     │   выход #2  (приоритет 20, резерв)
                     не расшифр.   │   выход #3  (приоритет 30, резерв)
                                    └─────────────────────────────────────────┘
          ▲                                   ▲
          │ self-service конфиги              │ SSH (paramiko) — установка, клон,
          │                                   │ синхронизация, чтение здоровья
     ┌──────────┐                        ┌──────────┐
     │  юзеры   │                        │  панель  │  ← это приложение («Hub»)
     └──────────┘                        └──────────┘     хранит всё состояние+секреты;
                                                           сама трафик НЕ пропускает
```

**Сама панель не пропускает VPN-трафик** — это малозаметный control plane, который
управляет каждой нодой по SSH и достукивается до локальных админ-API нод через SSH-туннели
по требованию. БД панели — единственный источник правды; ноды сводятся (converge) к ней.

Выход в пуле панель администрирует **только через его гейт** (SSH-ProxyJump): DPI в
регионе с цензурой часто рвёт прямое SSH-рукопожатие Hub→выход на «грязных» диапазонах, а
гейт до выхода достукивается, поэтому управляющий SSH туннелируется через гейт (сам гейт
только пересылает байты и к выходу не аутентифицируется). Прямого соединения Hub→выход
панель **не открывает сама никогда**, автоотката нет — если путь через гейт не поднялся,
операция падает с понятной ошибкой (а не виснет на DPI). Порядок раскатки: сначала гейт,
затем выходы, которые к нему привязываются; раскатка выхода требует, чтобы гейт пула был
известен заранее. На случай, когда выход недоступен через гейт, в «Серверах» есть кнопка
**«Напрямую ⚠»** — разовая диагностика прямым подключением, с предупреждением, что трафик
пойдёт в обход гейта. Так «добавить выход через сайт» работает и для флагнутых диапазонов.

## Что она умеет (восемь задач, под которые сделана)

| # | Возможность | Как |
|---|-------------|-----|
| 1 | **Разворачивать гейты** (L4-релеи насквозь) | `nftables` DNAT + крошечный демон health-check на Python, доставляемые по SSH; пропускает шифротекст, не расшифровывает |
| 2 | **Разворачивать выходы** (VLESS + AmneziaWG) | Ставит mainline 3x-ui, создаёт inbound VLESS+Reality+Vision, разворачивает контейнер AmneziaWG — всё с общей идентичностью пула |
| 3 | **Администрировать конфиги клиентов** | Self-service: юзер добавляет устройства, получает QR / ссылку / файл (AmneziaWG — `.vpn` для AmneziaVPN на Android/ПК, и отдельный WireGuard-style `.conf` для iOS/iPhone); один конфиг на устройство, валиден на весь пул |
| 4 | **Проверять доступность — два независимых среза** | Hub → каждый сервер (плоскость управления) **и** каждый гейт → выходы своего пула (реальный путь клиента, читается из демона гейта) |
| 5 | **Фейловер при потере выхода** | **Делает сам гейт** (active/standby с гистерезисом); панель задаёт приоритеты и шлёт список членов пула |
| 6 | **Бэкапить себя** | Консистентная онлайн-копия БД панели + секреты для восстановления, ежедневно в Telegram и по запросу |
| 7 | **Мониторить состояние** | Сохранённый снапшот, отрисованный на админ-странице и в Telegram; почасово + по запросу |
| 8 | **Уведомлять через Telegram — даже когда Telegram заблокирован** | Настраиваемый API-base + реверс-прокси, который панель может поднять на выходе одной командой (DuckDNS + Let's Encrypt → `api.telegram.org`) |

## Ключевые понятия

- **Пул (pool)** — криптоидентичность (пара ключей Reality + shortIds + spiderX + порт,
  и серверный ключ AmneziaWG + PSK + параметры обфускации + порт), сгенерированная один
  раз в панели. Каждый выход, добавленный в пул, разворачивается как её **клон**.
- **Выход (exit)** — сервер, который запускает VPN и выходит в интернет. Принадлежит
  одному пулу. Имеет `priority` (меньше = предпочтительнее) и `sync_state` (трафик идёт
  только на `synced`-выходы).
- **Гейт (gate)** — релей в регионе с цензурой перед пулом. К нему обращаются клиенты.
- **Маршрут (route)** — гейт **+** пул. Клиент выбирает маршрут сам — из тех, к которым ему
  открыт доступ по группе. Сменить регион выхода = выбрать другой маршрут; конфиг при этом
  не меняется.
- **Роли.** `admin` — полный доступ, включая управление ролями людей; `operator` — то же над
  парком, клиентами, группами и маршрутами, **кроме** управления ролями; `client` — конечный
  пользователь. У каждой учётки на странице «Пользователи» видно, **кем она заведена**.
- **Группы доступа.** Пользователь может состоять в нескольких группах; маршруту назначаются
  группы, которым он разрешён. Клиент видит маршрут, если делит с ним хотя бы одну группу;
  маршрут без групп недоступен никому. Персонал (admin/operator) видит и может делать конфиги
  по **всем** включённым маршрутам, минуя группы.

## Быстрый старт (Docker)

```bash
cp .env.example .env
# отредактируйте .env: задайте PANEL_SECRET_KEY (openssl rand -base64 48) и ADMIN_PASSWORD
docker compose up -d --build
# по умолчанию панель публикуется на 127.0.0.1:8080 (см. PANEL_BIND)
```

Заходите через SSH-туннель (панель держит доступы ко всему парку — не выставляйте её
голой наружу):

```bash
ssh -L 8080:127.0.0.1:8080 root@<хост-панели>
# затем откройте http://127.0.0.1:8080 и войдите админом из .env
```

### Публичный HTTPS

Есть два оверлея:

```bash
# A) у вас свободны порты 80/443 и домен указывает на хост панели:
docker compose -f docker-compose.yml -f deploy/docker-compose.tls.yml up -d --build

# B) порты 80/443 заняты / нужен бесплатный TLS без них — DuckDNS DNS-01,
#    отдаётся на :8443 (сначала задайте PANEL_DOMAIN + DUCKDNS_TOKEN в .env):
docker compose -f docker-compose.yml -f deploy/docker-compose.duckdns.yml up -d --build
```

## Поднять парк (всё из интерфейса)

Всё ниже делается в браузере — **как только SSH-доступ сервера попал в панель, вы на него
больше не заходите.** В этом суть: добавил сервер через сайт — он сам себя настроил.

1. **Пулы → создать пул** (`eu`). Панель генерирует общую криптоидентичность.
2. **Серверы → добавить ноду** для гейта: роль = *gate*, его публичный IP + SSH.
   Добавьте гейт **до** раскатки выходов: выходы на флагнутых диапазонах панель ставит
   *через* него (SSH-ProxyJump), иначе прямое SSH Hub→выход может не пройти.
3. **Серверы → добавить ноду** для каждого выхода: имя, публичный IP, SSH root-доступ,
   роль = *exit*, пул = `eu`. Затем **Развернуть** — панель (при необходимости через гейт)
   ставит 3x-ui, пинит Xray, создаёт VLESS-inbound с ключами пула, разворачивает контейнер
   AmneziaWG, закаляет машину и синхронизирует её в пул. Повторите для каждого выхода;
   задайте `priority`, чтобы один был основным, а остальные — резервом.
4. **Маршруты → создать маршрут**: выберите гейт + пул, затем **Поднять релей** — панель
   ставит на гейт демон health-check, нацеленный на выходы пула (в порядке приоритета).
5. **Группы → создать группу**; на вкладке **Маршруты** отметьте, какие маршруты ей доступны,
   а на вкладке **Группы** — каких пользователей в неё включить.
6. **Пользователи → создать пользователя** (по умолчанию — клиент; операторов/админов заводит
   только админ). Он заходит, **выбирает доступный маршрут**, добавляет устройства и получает
   конфиги. Готово.

Нарастить ёмкость позже = добавить выход в пул, **Развернуть**, затем заново **Поднять
релей**, чтобы гейт узнал о новом члене. Потеря выхода действий не требует — гейт
переключится сам.

## Фейловер подробно

На гейте работает небольшой демон (`/usr/local/bin/vespn-relay-daemon.py`, systemd-юнит),
который:

- читает членов пула (в порядке приоритета) из `/etc/vespn-relay/members.json`;
- TCP-пробит сервисный порт каждого выхода раз в несколько секунд, с **гистерезисом**
  (член должен пройти/провалить пробу *дважды* подряд, чтобы сменить статус — не дёргается
  от одной неудачной пробы);
- переписывает свою таблицу `nftables` так, чтобы DNAT указывал на **единственный
  живой выход с наивысшим приоритетом** (active/standby). Когда тот падает, трафик уходит
  на следующий живой; когда восстанавливается — возвращается обратно.

Гейт пересылает только шифротекст. Клиенты ничего не замечают — тот же IP (гейт), тот же
конфиг. Панель не в тракте данных, и для фейловера её работоспособность не нужна.

## Мониторинг и алерты

**Серверы → Мониторинг** (и Telegram-бот) показывают два намеренно разделённых среза, и
**ни один не делает прямого Hub→выход** (выходы проверяются только с их гейта):

- **Управляемость: Hub → ноды** — может ли панель управлять нодой своим реальным путём: до
  гейтов напрямую (SSH), до выходов — через их гейт (TCP-проба SSH-порта выхода **с гейта**).
  Это плоскость управления; связность клиента она **не** отражает.
- **Клиентский путь: гейт → выходы** — достижимость выходов с их гейта по портам трафика
  (VLESS/AWG), плюс живое состояние релей-демона: какие выходы он видит живыми, какой активен
  прямо сейчас и сколько раз активный выход «дёргался» (флаппинг) за последний час.

Проверки идут почасово (настраивается), по кнопке на странице и по `/check` в Telegram.
Эскалируются как алерты только клиентозначимые состояния (гейт упал, демон релея мёртв,
**нет** живого выхода, флаппинг).

**Трафик по конфигам.** Отдельная страница **Трафик** (админ/оператор): сколько у каждого
пользователя конфигов и сколько трафика по каждому — за день и всего. Счётчики снимаются
периодически **через гейт** (VLESS — API 3x-ui, AmneziaWG — `awg show transfer`), суммируются
по пулу и накапливаются с учётом сбросов счётчиков. Прямого Hub→выход при сборе нет.

## Telegram-бот (работает из заблокированного региона)

Опционально. Работает фоновыми потоками внутри процесса панели; спит, пока не заданы токен
+ chat id (в **Мониторинг → настройки бота**, хранится в БД в зашифрованном виде).

- **Ежедневно:** бэкап (см. ниже) + сводка статистики.
- **Почасово:** мониторинг; шлёт админу алерт, когда набор проблем меняется.
- **Команды:** `/check` (проверить сейчас), `/status` (последний снапшот), `/backup`
  (прислать сейчас).

**Проблема заблокированного Telegram, решённая через гейт.** `api.telegram.org` недоступен
из региона, где живут гейт/панель. На **каждом выходе** автораскатка поднимает реверс-прокси
Caddy, слушающий только `127.0.0.1` (наружу ничего не торчит). Бот не ходит ни в Telegram
напрямую, ни к выходу напрямую: он открывает SSH-туннель **Хаб→гейт→выход** и обращается к
прокси через него (SSH шифрует хоп, Caddy добавляет TLS до Telegram). Выход для ТГ выбирается
**по приоритету** (`Node.priority`): бот берёт первый достижимый и переключается на следующий,
если тот отвалился. Так закрыт последний прямой Hub→выход.

Поле **API-base** остаётся как ручной обход: если задать явный внешний URL (не
`api.telegram.org`), бот пойдёт по нему напрямую, минуя гейт (для отладки).

## Бэкап

`make_backup()` формирует `.tar.gz` с **консистентной** онлайн-копией SQLite-БД панели
(через backup-API SQLite — никогда не рваный файл) плюс `env.txt` с секретами для
восстановления (`PANEL_SECRET_KEY`, доступы админа, домен/токен DuckDNS, …). Отправляется
ежедневно в Telegram и по `/backup`.

> ⚠️ **Бэкап чувствителен.** Вместе с `PANEL_SECRET_KEY` он расшифровывает любой
> сохранённый доступ к ноде. Держите Telegram-чат приватным; относитесь к архиву как к
> мастер-ключу.

## Модель безопасности и заметки

- **Гейт по замыслу не доверенный.** Он всегда видит только шифротекст и не держит ключей,
  поэтому его безопасно крутить на враждебной территории. Zero-trust — это и есть вся суть.
- **Секреты в покое.** SSH-пароли, API-токены 3x-ui и ключи пула шифруются в БД через
  Fernet ключом, производным от `PANEL_SECRET_KEY`. Его ротация намеренно делает их
  нечитаемыми (введёте заново из UI).
- **Ноды закаляются автоматически** при провижининге: панель 3x-ui слушает только
  `127.0.0.1` (доступна исключительно через SSH-туннель панели), публичный
  subscription-сервер выключается, `fail2ban` отключается (иначе он забанит гейт или
  панель при всплеске подключений), а Xray-core пинится на заведомо рабочую версию.
- **Защищайте панель.** Она держит доступы ко всему парку — прячьте её за SSH/HTTPS,
  никогда не выставляйте напрямую, и поставьте `SESSION_HTTPS_ONLY=true`, как только она на
  HTTPS.
- Приватные ключи клиентов AmneziaWG генерируются на стороне панели и живут **только** в
  выданном конфиге (внутри строки `vpn://`); на ноду они никогда не попадают.

## Стек

FastAPI · SQLAlchemy (SQLite) · Jinja2 · paramiko (SSH + туннели) · bcrypt ·
`cryptography` (генерация ключей WG/Reality + Fernet). Без брокера сообщений, без внешней
БД — один процесс, один файл SQLite в volume. Ноды крутят mainline 3x-ui + официальный
контейнер `amneziavpn/amneziawg-go`; гейты — `nftables` + демон на ~90 строк из stdlib.
